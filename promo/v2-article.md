# 给 AI 装上恋人模式：从一个技能包到情感陪伴 Agent 的进化

> 一句话概括：把「恋人」做成一个能被任意 AI Agent 加载的技能包，v2 起往 Agent 级进化——
> **重活离线做，在线只注入 500 Token 以内。**

## 一、先说要做的事

AI 陪伴赛道这两年很热，但用下来会发现几个普遍问题：

| 痛点 | 具体表现 |
|---|---|
| 绑定平台 | 只能在某个 App 里用，换框架就没了 |
| 人设写死 | 预设角色不能深度自定义，想要个「会嘴硬的傲娇」得看运气 |
| 数据不透明 | 聊天记录存云端，不知道被拿去做什么 |
| 不开源 | 想改个语气？没门 |

而不同 AI 框架各有各的技能体系，但**「恋人模式」的核心需求其实是一致的**：人设配置 + 记忆 + 情感反馈。

所以思路是：**把这套逻辑抽成独立模块，做成通用技能包。** 存储路径可配、不依赖特定框架、JSON 配置驱动。

这就是 **Love Companion**：一个开源的 AI 恋人陪伴技能包，8 种预设人设即插即用。

目前是 **v2.0.0**。这篇讲两件事：**v1 的基础设计**，以及 **v2 往 Agent 级进化时做的那些取舍**。

## 二、v1：把「恋人」拆成能配置的结构

### 2.1 人设的七维模型

不是填个名字就完了。一套完整人设拆成 **7 个维度**：

```
┌─────────────────────────────────────┐
│  基础信息：名字、年龄、身份          │
│  性格结构：核心特质 + 小脾气         │
│  对话风格：口头禅、emoji 习惯        │
│  背景故事：相遇场景、关系定义        │
│  相处模式：主动/被动、回应速度       │
│  亲密尺度：1-5 级分级                │
│  内容边界：绝对不做的事              │
└─────────────────────────────────────┘
```

**这里有个关键的设计决策**：性格拆成「核心特质」和「小脾气」两个子字段。

因为完美的人设不真实。**有缺点才立得住**——傲娇型会嘴硬心软，病娇型会过度在意你，这些「缺陷」反而让角色鲜活。只写「温柔体贴」得到的是客服，不是恋人。

### 2.2 记忆系统

```
┌──────────────┐        ┌──────────────┐
│  短时记忆     │        │  长时记忆     │
│ (框架自带)    │        │ (Skill 维护)  │
│              │        │              │
│ 当前对话上下文 │  ←→   │ 用户喜好      │
│ 最近几轮聊天   │        │ 重要日期      │
│              │        │ 情绪轨迹      │
└──────────────┘        └──────────────┘
                         ↑
                  手动 / 自动 双通道
```

- **手动通道**：`/恋人记忆 我喜欢喝三分糖去冰`
- **自动通道**：从对话里识别关键信息，自动持久化

### 2.3 安全合规

- 亲密尺度 **1-5 级分级**，4-5 级有明确内容边界约束
- 本地存储，**数据不出设备**
- 强调「**AI 陪伴 ≠ 真实关系**」，所有文件带免责声明

|---|---|---|---|

| 2 | 🌸 温柔治愈 | 温婉 | 贴心细腻，永远在你身边 |
| 3 | 🧊 傲娇高冷 | 冷月 | 嘴硬心软，欲擒故纵 |
| 4 | 🍬 活泼可爱 | 糖糖 | 软萌黏人，撒娇担当 |
| 5 | 🍷 成熟知性 | 苏雅 | 知心大姐姐，稳重温柔 |
| 6 | 🔥 腹黑撩人 | 苏妖 | 暧昧高手，让你心跳加速 |
| 7 | 🌷 纯情害羞 | 小雪 | 初恋般的悸动，慢慢来 |

## 三、v2：为什么不能只是「加功能」

v1 发布后收到最多的反馈是「记忆不够用」「不够像我认识的那个人」。顺着加功能听起来合理，但很快就撞到三个硬约束：

1. **Token 是有限的。** 每轮对话塞进去的记忆、人设、画像越多，能留给真正聊天内容的空间就越少。无节制地堆，回复质量必然下降。
2. **隐私不能打折。** 想「更懂用户」就需要更多数据，而原始聊天记录是最敏感的东西。把它塞进每轮上下文，既贵又危险。
3. **真实性不能编。** 一旦模型开始「脑补」记忆，用户会立刻发现——那比不记得更伤人。

所以 v2 定了一条贯穿所有模块的红线：

> **离线重处理、在线轻注入。**

特征提取、记忆抽取、人格编译、网页抓取、语气改写 **全部在对话间隙离线完成**，原始内容绝不进对话；在线只读取离线产出的**短摘要**。单轮额外系统开销**硬约束在 500 Token 以内**。

### 3.1 在线 / 离线边界

```
┌─────────── 离线（重活，不占对话 Token）───────────┐
│ 任务队列    注册 · 调度 · 重试 · 落盘             │
│ 记忆系统    无感采集 → 六类记忆 → 检索索引        │
│ 人格克隆    素材摄取 → 三层提取 → 人格库 → 编译摘要 │
│ 用户理解    流式采集 → 两级分析 → 相处指南        │
│ 语气守门    三层黑名单校验（后处理）              │
│ 趋势感知    抓取 → 解析 → 流行语/热点提炼         │
└────────────────────┬───────────────────────────┘
                     │ 产出「注入摘要」（短文本 + Token 计数）
                     ▼
┌─────────── 在线（轻注入）───────────────────────┐
│ 运行时读取摘要 → 拼进 System Prompt              │
│ 预算：相处指南<200 · 记忆Top-3<150 · 人格指令<100 │
│       趋势<50 · 关怀话术<80      合计 ≤500 Token │
└────────────────────────────────────────────────┘
```

**预算不是建议值，是硬约束。** 注入前统一过一遍计数，超限就截断或直接拒注。
另外按「实际有内容的模块」分配额度——空模块不占额度，否则「没内容的高优先模块」会把「有内容的低优先模块」挤成 0。

### 3.2 伴侣人格克隆

这是 v2 最受欢迎的能力。导入聊天记录 / 日记 / 社媒导出，蒸馏出一个**像本人**的恋人。

三层提取，回写进人设：

| 层 | 提取什么 | 效果 |
|---|---|---|
| 声线 | 口头禅、标点习惯、句子长短、emoji 用法 | 说话像本人 |
| 思维 | 关心方式、决策倾向、话题偏好 | 反应像本人 |
| 性格 | 核心特质、小脾气 | 立得住 |

**一个重要的边界**：蒸馏**无权改动**亲密尺度、内容边界、对用户的称呼。这三样只认用户的显式设置。

原因很简单：这是恋人陪伴，用户已经手动设好了安全边界，一个从聊天记录里跑出来的自动化流程不该有权覆盖它。安全感不能靠模型自觉。

配套机制：增量 merge（越用越像）、对话纠偏（`/恋人纠偏 不该这样说 → 应该这样说`，下一轮立即生效）、版本回滚。

### 3.3 六类记忆，而不是一个列表

v1 的记忆是个扁平列表，用久了会长成几百条互相淹没的流水账。v2 按性质分成六类：

**事实 / 偏好 / 里程碑 / 共享事件 / 情绪 / 人设特征**

召回时走多路打分：语义相关 + 时间新旧 + 重要性 + 关系路径，取 Top-3。并且**随时间自然衰减**——三个月前提过一次的小事，不该和昨天刚说的心事抢同一份预算（未被召回的记忆重要性半衰期为 30 天）。

被记住的东西要能溯源：每条注入的记忆都带条目 id，`/恋人解释` 可以告诉你「上一轮为什么这么说，依据是哪条记忆」。

### 3.4 恋人式的用户理解

想「更懂你」，但**只存特征，不存原文**。

采集是流式的、增量的，落盘的是「偏好三分糖去冰」这类特征，而不是你当时说的那句话原话。采集开关随时可关。

识别到依恋类型后，关怀方式**差异化**：

| 依恋类型 | 给它什么 |
|---|---|
| 焦虑型 | 确定性 —— 明确说「我在」 |
| 回避型 | 空间 —— 不追问、不逼迫 |
| 安全型 | 自然陪伴 |
| 恐惧型 | 两者都给 —— 先给空间，再给确定性 |

这一项是最容易被忽略、但体感差异最大的。同一句「我今天很累」，对焦虑型说「那你自己静静」是伤害，对回避型说「你到底怎么了」是压迫。

### 3.5 语气守门：拦下「AI 腔」

模型写恋爱对话有个通病——听起来像客服。三类高发模式：

- **空洞安慰**：「别难过啦，一切都会好起来的」
- **客服式共情**：「我理解你的感受，这确实很不容易」
- **替用户断言情绪**：「你现在一定很焦虑吧」

还有一类是**万能陪伴宣言**：「无论发生什么，我都会一直陪着你」——单看没错，但每轮都说就成了复读机。

v2 加了一层后处理专门拦这个：三层黑名单（禁用词 / 结构模式 / 风格偏差）+ 短句节奏控制 + 四档强度，深夜还会自动放轻。**它不是让恋人变冷淡，是让它别像机器人。**

### 3.6 主动关怀

三道闸门：**冷却**（刚关怀过不重复）、**静默时段**（不在你睡觉时打扰）、**频次**（一天最多几次）。

四类信号：低落、纪念日、深夜、久未联系。

关怀话术不是套模板，而是按人格声线改写，并且遵守依恋差异化。预算 ≤80 Token。

### 3.7 趋势感知：只要「一句能开口的话」

很多人做「AI 感知热点」，最后变成爬虫框架——接十几个平台，用户一个也用不上。

恋人陪伴场景真正需要的不是「全网接入能力」，而是**一句能开口的话**。

所以 v2 只留 3 个真用得上的源，核心逻辑是：

- `talkability()` —— 这个话题**适不适合跟恋人聊**
- `opener()` —— 怎么**开口**才自然

热点本身没意义，「今天看到 XX，想起你上次说……」才有意义。而且不合规的话题、触及内容边界的，一票否决。

### 3.8 多模态：发图是「递生活」，不是配图

恋人发照片，不是给文案配图，是**把此刻的生活递给你看**。

所以拍什么由人设的「关心方式」决定，能拍多近由「亲密尺度」决定，不能拍什么由「内容边界」决定。

### 3.9 控制与安全感

能力越强，越要把控制权还给用户：

- `/恋人解释` —— 可解释面板，回复依据可查
- `/恋人开关 [模块]` —— 每个模块独立开关
- `/恋人修正 [特征路径] [0-1]` —— 改 Agent 对你的理解，0 = 别用这条
- `/恋人遗忘 [名字]` —— 人格 + 关系 + 该关系的记忆一并清除
- `/恋人导出全部` —— 一键导出全部本地数据

**数据始终在本地。** 文件损坏时会自动隔离为 `*.bad-<时间戳>` 并降级到默认值，不会静默丢数据。

## 四、技术架构

```
love-companion/
├── SKILL.md                 # 技能主文件
├── README.md
├── LICENSE                  # MIT
├── scripts/
│   ├── manager.py           # v1 配置与记忆管理（全部保留）
│   ├── core/                # schema · 设置 · 数据可靠性 · 隐私脱敏 · 内容边界
│   ├── pipeline/            # 离线队列 · 注入器 · 调度器 · 在线编排
│   ├── memory/              # 六类记忆：采集 · 召回 · 衰减
│   ├── persona/             # 人格克隆 + 镜像 + v1 适配层
│   ├── user/                # 用户理解 + 依恋规则引擎
│   ├── style/               # 语气贴合 + AI 腔守门
│   ├── care/                # 主动关怀
│   ├── trends/              # 趋势感知
│   ├── multimodal/          # 配图计划
│   ├── panel/               # 可解释面板 + 控制开关
│   └── migrate/             # v1 → v2 无损迁移
├── tests/                   # 296 项回归测试
└── references/
    ├── personas.md          # 8 套预设人设模板
    ├── commands.md          # 完整指令手册
    └── instructions.md      # 详细教程
```

**零第三方依赖，只用 Python 标准库。** 不需要装任何东西，克隆即可用——这一点是刻意的：技能包要能被用户直接扔进技能目录，不能要求他先配环境。

在线唯一入口是一个 `Session`：`prepare()`（回复前准备）→ `after_reply()`（回复后沉淀）→ `proactive()`（空闲时主动关怀）。其余模块全是离线跑。

## 五、从 v1 升级

**无需任何操作，直接拉取新版本即可**——v2 是 v1 的严格超集：

- 8 套预设、全部 `/恋人…` 指令、`manager.py` 的 API 与数据目录**全部保留**
- 老的 `persona.json` / `memory.json` 直接可读
- 迁移会**先备份再写入**，备份目录形如 `backup_v1_<时间戳>/`，随时可回退

想先看一眼迁移会做什么（不改任何文件）：

```bash
python scripts/migrate/migrate_v1.py --dry-run
```

重复执行是安全的（幂等），已迁移过的文件不会被再次改动。真实数据实测无损。

## 七、一些工程上的取舍

做这个项目踩过的坑，记几条值得说的：

**1. 两套人设是大忌。**
一开始想做「v1 人设 + 另一套蒸馏人格」并存。问题是会出现**两个人设**：`/恋人配置` 改的是 A，蒸馏出来的是 B，用户完全说不清哪个生效。后来改成：三层提取只是**中间产物**，一律回写进 v1 的字段，人设真相源永远只有一个。

**2. 内容边界要用关键词，不是整句。**
用户写的是祈使句「不谈前任」，但真正的禁区是「前任」这个词。拿整句去匹配永远命中不了。抽成一个共用工具把祈使句还原成关键词，被「回复自检 / 趋势取舍 / 配图元素」三处复用。

**3. 空壳人设不该注入。**
默认人设自带「主动程度=中 / 亲密尺度=3」。如果用户根本没设过，拿这个默认值编译出行为卡注入进去，就是纯噪音——**默认值不是用户意图**。改成能不注入就不注入。

**4. 宿主机是黑盒。**
技能包是被别人的 Agent 框架加载的，不知道宿主什么时候空闲、有没有定时任务。所以离线管线的触发必须设计成「谁来调都行」，而不是假设有一个常驻进程。

## 八、最后

开源的意义在于：**不让「AI 恋人」只存在于封闭产品里。**

通用的、可自定义的、数据在本地的——这才是 AI 陪伴该有的样子。

v2 想往前再走一步：不只是「能被加载」，而是**真的像一个懂你的人**。但这件事的底线是——**懂你不等于扒光你**。所以离线重处理、只存特征、边界只认用户显式设置，这些不是加分项，是前提。
